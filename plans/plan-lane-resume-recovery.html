TARS: Safe Lane Resume and Recovery

Issue #1 — the coordinator can record a prompt delivery before an agent ever works it, and an interrupted or outdated coordinator can leave a lane with incomplete or stale state. Operators need an evidence-based way to know whether a lane needs action, is already progressing, has completed delivery, or requires sessions to be re-created — and to resume it only with explicit intent.

Problem details

  • ReviewLoopCoordinator.processLane (automations/review-loop/lib/coordinator.mjs) checks a session is currently idle before sending, then journals the event key in dispatched_events. The journal is append-only idempotency, but a delivery can still be recorded without the agent acting (session dies after the check, watcher interrupted mid-send, blank re-created session never prompted). Nothing ever re-examines those records.
  • The only today-view is status (one line per lane) or raw SQLite reads. There is no command that derives the next pending action from durable handoff files + lane state + AoE session liveness.
  • Goals: identify the next pending action, avoid duplicate agent work, report ambiguity / inactive sessions clearly, and gate any dispatched recovery action behind explicit operator intent.

Design overview

Add a read-only analysis plus an explicitly-gated recovery as one command:

node automations/review-loop/cli.mjs lane resume (--worktree <path> | --issue <number>) [--dispatch] [--create-sessions]
No flags = pure diagnosis. It never sends prompts and never mutates lane state or AoE sessions (it reads AoE session metadata via listSessions/runtimeSessions for liveness only). Action flags (--dispatch, --create-sessions) each enable exactly one recovery action and only when the verdict supports it; otherwise the command refuses with the reason and a non-zero exit.

Implementation is additive: a new lib/recovery.mjs, two small read helpers on StateStore, three existing coordinator helpers promoted to named exports (no behavior change), a new CLI subcommand, tests, and docs.

Verdict model

analyzeLane returns exactly one verdict plus reasons and, when determinable, the single next event.

VerdictMeaningRecovery allowed
blockedLane state is blocked, or an undispatched event exceeds max_rounds (coordinator would block).none
no_actionNothing pending: delivery complete (approved lane, no reopen), or healthy lane awaiting the agent's next handoff.none
needs_dispatchExactly one actionable pending event (undispatched, in round/iteration limits) whose target session is idle/waiting.--dispatch
stale_deliveryA previously recorded delivery has no advancement evidence, the target session is idle/waiting, and it is older than a staleness threshold. The recorded delivery likely never took effect.--dispatch (clears the stale journal marker first, then re-dispatches)
in_flightAlready progressing: the target session is busy/running, or a recent dispatch (or the compacting transition) still has no completion — do nothing, avoid duplicate work.none
sessions_missingA registered OpenCode/Codex session is absent from AoE, or its id no longer matches the lane's worktree and role; the lane cannot advance until re-created.--create-sessions (then re-analyze)
inactive_sessionsSessions exist but are dead or have no runtime record — dispatch would be futile and unsafe.none (operator stops/removes via AoE, then --create-sessions)
ambiguousMultiple actionable pending events, multiple unconfirmed deliveries, or lane state contradicts handoff evidence. List all candidates; never guess.none

Staleness threshold: a dispatched event older than STALE_AFTER_MS (10 minutes) with an idle target session and no advancement is reported as stale_delivery; younger than that it is reported as in_flight (plausibly being worked). The timestamp comes from the existing dispatched_events.created_at column.

Evidence sources and analysis steps

  1. Handoffs — handoffsFor (inbox + done) for actionable events, exactly mirroring the coordinator; additionally read in-progress and archive for advancement evidence.
  2. Lane row — state, phase, currentIteration, iterationCount, maxRounds, transition fields.
  3. Journal — the dispatched_events keys and their created_at timestamps.
  4. AoE — listSessions (registered ids still exist?) and runtimeSessions({includeDead:true}) (idle / waiting / running / dead).

Ordered decision procedure (first match wins):

  1. Lane blocked → blocked. Lane approved with no reopen event → no_action.
  2. Registered session id(s) absent from listSessions → sessions_missing (name the missing role). A matching id whose worktree path or tool differs from the lane registration is also treated as sessions_missing — it is never a usable dispatch target.
  3. A registered session that exists but is dead or has no runtime record → inactive_sessions (checked before evaluating any pending or dispatched event candidates).
  4. Undispatched event over max_rounds (within iteration) → blocked (max_rounds).
  5. Multiple actionable pending events → ambiguous (list them). Exactly one → inspect its target session: dead → inactive_sessions; busy → in_flight; idle/waiting → needs_dispatch.
  6. phase === "compacting" → in_flight (the coordinator's plan→build transition owns it; a watcher pass advances it).
  7. No pending events. Inspect dispatched-but-unconfirmed events (no advancement, within current iteration and max_rounds): none → no_action; >1 → ambiguous; exactly one, older than threshold + target idle → stale_delivery; busy → in_flight; recent → in_flight; dead → inactive_sessions.
  8. Contradiction (lane state claims reviewing/implementing but no handoff or journal evidence exists) → ambiguous with the contradiction listed.

Advancement for event E (workflow W, round R): any handoff with workflow_id === W and (round > R or responds_to === E.id), anywhere in the queue. This is the evidence that the lane actually moved past the recorded delivery.

Recovery actions

  • --dispatch (verdicts needs_dispatch, stale_delivery): for stale_delivery, first delete that event's dispatched_events row (the operator's explicit retry intent), then run exactly one dispatchLane(lane) pass. The clear and the dispatch run under a shared per-lane claim (SQLite lane_claims) so a concurrently polling watcher cannot observe the cleared marker and re-send; processLane takes the same claim. dispatchLane dispatches at most one event per call (every branch ends in break), so this is exactly one prompt, through the same code path the watcher uses — no duplicated prompt-building logic, and the normal state transitions apply. If the pass produces no action, report why.
  • --create-sessions (verdict sessions_missing): re-add only the missing role via AoeClient.addSession, re-register the new id in the lane row, then re-analyze. Never overwrite a session id that still exists. Combined with --dispatch, a newly-created (blank) OpenCode session can then receive the pending prompt directly. A re-created session is blank; the report notes the operator may need to rebuild agent context manually for non-event work.
Safety guarantees: dispatch only to idle/waiting sessions; never auto-recreate without --create-sessions; never dispatch without --dispatch; re-dispatch only after an explicit marker clear; multiple candidates → ambiguous refusal.

Tests

Run: node --test automations/review-loop/test/*.test.mjs. Recovery tests use a temp SQLite StateStore, a FakeAoe (listSessions / runtimeSessions / runningSessions / send), and real handoff files in a temp worktree — same fixtures as the coordinator suite.

  • approved lane with no reopen event → no_action; blocked lane → blocked.
  • single pending implementation-response, Codex idle → needs_dispatch; --dispatch sends to Codex exactly once and journals it.
  • two pending events → ambiguous, --dispatch refuses.
  • dispatched event, no advancement, Codex idle, journal old → stale_delivery; --dispatch clears the marker and re-sends exactly once.
  • dispatched event, no advancement, Codex busy → in_flight; --dispatch refuses (no duplicate work).
  • registered Codex session absent → sessions_missing; --create-sessions adds and re-registers it; combined --dispatch sends the pending prompt.
  • Codex runtime dead → inactive_sessions; --dispatch refuses.
  • fresh registered lane, no handoffs → no_action (awaiting agent).
  • round beyond max_rounds undispatched → blocked (max_rounds).

Out of scope

  • Auto-fixing a dead but existing session; the operator removes it via AoE and recovery then re-creates it with --create-sessions.
  • Rebuilding an agent's working context inside a blank re-created session beyond dispatching the pending event.
  • Changing the watcher's normal dispatch path or the handoff protocol.

# Spike: evidence needed for a navigation diagnosis

Status: findings recorded in [the spike report](spike-navigation-evidence-findings.md). This remains an investigation task, not the production importer. Do not begin the post-spike design activities until the operator has reviewed the findings.

## Question

Can TARS give an operator a defensible account of repeated reads/searches and exploration breadth using a deterministic projection of native Codex and OpenCode evidence? If not, how much native session context must a separate analyst inspect to understand each agent's task and rationale?

## Probe

1. Use a disposable, small repository and new TARS-style author/reviewer sessions. Give each harness a task that requires finding a relevant file among plausible distractors, and one that legitimately requires reading several files. Include deliberate full reads, partial reads, an author's full reread after an edit or feedback for verification, repeated searches, a compaction where supported, and shell variants (`rg`, `grep`, `find`, `cat`, `sed`, `head`, pipelines, compound commands, and an allowlisted wrapper such as `rtk` around each). Include reviewer rounds where a previously read file changes in one commit and stays unchanged in another; preserve each handoff commit SHA. Capture native Codex Rollout Trace and OpenCode session export with the supported CLIs. Keep all raw evidence in harness-owned or temporary locations outside the repository; do not commit transcripts.
2. Inventory the native schema without publishing prompt, source, or tool-output content: session and turn IDs, timestamps, tool names, command strings versus parsed arguments, input target fields, search queries, output size/status/truncation, token metrics, compaction markers, and links between a read and later edits or answers. Record missing fields and any ambiguity in role/session attribution. Do not assume structured events imply structured navigation actions.
3. Build a temporary prototype that emits an ordered metadata trail per role and logical block, including handoff commit SHAs. Check which command variants can be classified reliably; distinguish files named in a command, files whose content was visible in its output, full-file reads, partial reads, search-result snippets, and filename-only search results. Preserve each complete shell command and any wrapper chain. For an allowlisted wrapper, test whether its underlying command and arguments can be deterministically recovered without changing provenance; otherwise classify the operation as unknown. Count breadth only for files whose contents were visible. Compare it against the native record for within-role repeated full reads, exact and similar repeated searches, exploration breadth, compaction resets for both reads and searches, and changed-versus-unchanged files across reviewer commits. Mark every place where the projection loses context or misclassifies an operation. Treat ambiguous shell behavior as unknown, not as a confirmed read.
4. Try an analyst on the projected trail, a bounded native-content view, and the complete relevant native session context, with read-only repository access. Include prompts and tool outputs where they explain the agent's objective or exploration. Ask it to identify similar searches that pursued the same answer even when the query strings differ; compare that judgment and each resulting claim against the native record. Test whether deterministic selection rules can pick the needed context; if they cannot, measure the size and cost of passing complete context for each block or the full lane. Do not silently truncate or summarize away events.
5. Draft two sample operator reports: one with a strong navigation diagnosis, one where observed behavior has a plausible legitimate explanation such as rereading an edited file for verification. Lead with a lane-wide narrative and provide block-level detail only for notable patterns. Judge breadth in the context of each task and the work performed, without a fixed file-count threshold. For notable searches, report both intent and literal queries without redaction; keep other raw prompts, source contents, and tool output out of the report. Include the exact evidence pointers, coverage limits, and uncertainty. Check whether any proposed repository change is supported by inspection of the current repo structure.

## Decision record to produce

- Native fields and stable evidence pointers available for each harness, including evidence of compaction and output truncation.
- A command-classification coverage table: correctly classified, ambiguous, and missed read/search forms for each harness. Include wrapper handling, the granularity available for full versus partial reads, filename-only search results, and files whose contents were actually shown to the agent.
- The smallest analyst input that preserves enough task and rationale context, and whether selection is deterministic, analyst-directed, or complete native context at block/lane scale.
- Measured input size and estimated analysis cost for representative short and long blocks, including the over-budget stop point.
- A proposed report schema that separates observations, analyst hypotheses, supporting and contradicting evidence, unknowns, and optional repository changes.
- Explicit cases where TARS should report a symptom but decline to judge a read as avoidable, including missing compaction or read-extent evidence.

After reviewing this record, complete the [post-spike design activities](plan-active-lane-investigation.md#post-spike-plan-completion), including the high-level transient evidence-index design, before finalizing the implementation plan. The spike must not create a persistent TARS evidence store.

# Active-lane investigation requirements

Status: requirements captured from the discussion of [issue #18](https://github.com/satwikhebbar/tars/issues/18) on 2026-09-25. This document records the intended product behavior; it is not an implementation plan. Where it differs from the issue, the decisions below supersede the issue's proposed first cut.

## Purpose and TARS's role

TARS is a repo-agnostic, configurable orchestrator for coding agents. Its investigation capability should help the operator reflect on how an active lane's author and reviewer used their harnesses, then recommend improvements to the repository or its agent workflow. TARS should rely on evidence that the harnesses already produce. It should act as a lens over that evidence, not as a third-party trace collector or evidence store.

The initial built-in investigation is **repository navigation efficiency**. It should explain observable navigation behavior and symptoms across the lane, focusing on repeated reads and searches and the breadth of files explored. It may assess whether some exploration appears avoidable, while accounting for what the agent was trying to accomplish. A repository change is optional and must be grounded in both the observed behavior and the repository's current navigation aids. A later built-in question may examine risky workflow actions, such as a production deployment proposed in a plan, approved in review, and attempted during implementation. The first-cut design must admit that second question without implementing it now.

## Scope and invocation

- Investigation is on demand and advisory. The first cut does not send feedback into either lane role, change permissions, enforce policy, or emit real-time anomaly alerts.
- Only an **active TARS lane** can be investigated. TARS does not preserve investigation data or a closed-lane session mapping for retrospective reflection after lane close.
- Analyze **both author and reviewer roles across the lane to date**, rather than asking the operator to choose a time slice. The roles must both be idle when the investigation starts. If one role has not yet acted, say so.
- The first cut supports newly launched TARS-managed Codex and OpenCode role sessions. An explicit lane-start opt-in enables any native evidence that must be configured before launch; investigation remains off by default. Do not silently attach to already-running, standalone, or Codex Desktop sessions. If an opted-in lane uses an unsupported harness, reject that lane start with a clear error.
- An unavailable source for one role does not prevent analysis of the other role, but the result must prominently describe the resulting coverage gap. Ambiguous attribution must be reported rather than guessed.

## Native evidence and data ownership

- For Codex, enable its native Rollout Trace before a role session starts and read the resulting bundle in place. The trace is a Codex artifact, even if TARS selected its location at launch.
- For OpenCode, read its native session evidence on demand through a supported export or session interface. For a freshly launched AoE interactive role, TARS may obtain the native session ID through a transient, role-specific launch handshake: send a generated unique first prompt, enumerate native sessions, and accept an ID only when exactly one raw export contains that exact prompt. Never infer the mapping from launch time or working directory. TARS must not retain a second raw export.
- TARS may use its existing active-lane orchestration state to identify roles and sessions. It must not create a separate persistent investigation store for raw evidence, normalized events, references, or derived findings.
- Temporary processing data is discarded after the command. TARS must not put raw prompts, source contents, tool output, or trace artifacts in the worktree, Git history, or `.agent-handoff/`. An operator-requested report export is the explicit exception to the no-persistent-output default.
- The default result and exported report contain paths, timing, counts, other evidence metadata, and literal search queries when relevant. Do not redact queries for the operator's local CLI output or requested Markdown export, even if a query contains sensitive text. Omit other raw prompts, source contents, and tool output.
- Native evidence follows the harness's own retention and deletion behavior. The earlier proposed seven-day TARS retention profile no longer applies because TARS does not own that evidence. If native evidence disappears while a lane is active, report it as unavailable.

## Navigation analysis

- Partition the full lane into logical blocks using TARS handoffs, iterations, and role transitions. Preserve each handoff's commit SHA in analyst context so it can identify the relevant repository state. Compare behavior across blocks so patterns over time remain visible; the analyst may consult Git history when useful.
- Construct a deterministic evidence index before invoking an analyst. Include ordered tool events, direct file-tool targets, separately labeled paths inferred from shell commands or their visible output, outcomes, duration, and token usage where the harness exposes them. Treat command wrappers as part of normal harness usage: preserve the complete command and wrapper chain as evidence, then unwrap only an allowlisted wrapper (for example, `rtk`) to classify its underlying command. Attribute the navigation observation to the underlying command while retaining the wrapper and native event pointer for provenance. An unrecognized wrapper, or a wrapper whose arguments cannot be unambiguously recovered, is `unknown`; do not infer a read or search from its name alone. Do not assume native traces classify reads and searches at the granularity this question needs: commands may contain wrappers, pipes, compound operations, or several search variants. Do not describe inferred command paths as an operating-system audit of file access. The analyst input projection and the classification rules remain provisional until an evidence spike establishes what can be extracted reliably.
- Partition large sessions into logical blocks before estimating analysis cost. If the whole-lane investigation would exceed the configured analysis budget, stop before invoking the analyst. Show the block inventory and estimate, then let the operator either raise the budget for whole-lane coverage or select fewer logical blocks. Do not silently select blocks or ask the operator to guess a raw time interval. Label a narrowed result with its actual scope.
- Use the lane's **author harness** for any LLM analysis, matching TARS's current preflight pattern. Run the analyst in a separate session with read-only access to the worktree; do not add its prompt or output to either lane role's working session. The analyst may inspect native prompts and tool outputs when needed to understand the agent's objective and why it explored particular files. Determine through the evidence spike whether a bounded selection preserves enough context; do not assume it does. Native content examined by the analyst must not be copied into the default report.
- Distinguish measured behavior from interpretation. Treat repetition as occurring within one role; cross-role overlap is a separate observation. Distinguish full-file reads from partial reads and search results before flagging a repeated read; a partial revisit is not automatically a repeated full read. A compaction resets the agent's repository knowledge, so a subsequent full reread or repeated search is acceptable without flagging it as repetition. For the author, early reads usually build task context; a full reread after the author's own edit or after reviewer feedback may be a reasonable verification step, but remains a candidate for analyst judgment when there was no compaction. For the reviewer, rereading a file after a new commit changed that file is expected; flag a repeated full read only when that file has not changed since the reviewer's earlier full read and there was no intervening compaction. Use handoff commit SHAs and, where helpful, Git history to understand changes between review rounds. If the native evidence cannot establish read extent, compaction, or whether a file changed, report that gap instead of asserting an avoidable reread. Count a file toward exploration breadth only when part or all of its contents were shown to the agent; a filename-only hit or a command that scanned a file is insufficient. Judge breadth against the agent's task and resulting work, with no fixed excessive-file threshold. The analyst judges whether distinct but similar searches were pursuing the same answer and whether navigation suggests avoidable work, with each judgment tied to observed events and its rationale. Token use may be observable per turn without proving which read caused it. Label supposedly unnecessary reads as evidence-linked **hypotheses with uncertainty**, not as counterfactual facts. An agent's later self-assessment is self-report, not proof.
- Lead with diagnosis and symptoms, not prescribed fixes. When the evidence and repository inspection support a specific operator change, describe it and explain why it could help; otherwise state what remains unknown. TARS does not draft replacement prose or apply changes automatically in the first cut.

## Result and extensibility

- Print the investigation result through the CLI, with an optional operator-requested Markdown report export. Lead with a lane-wide narrative of repeated reads/searches and exploration breadth. Show block-level detail where a problem or notable pattern was found, without forcing an uneventful-block walkthrough. If no concerning pattern is supported, say so briefly with coverage and basic counts. Include evidence-linked diagnoses, optional supported recommendations, native evidence identifiers, coverage gaps, and the limits of each conclusion. For notable search behavior, describe the search intent and show the literal query as well.
- Keep the question interface extensible to operator-configured questions and a later risky-workflow investigation. Each question should reuse the same active-lane evidence access, logical blocks, provenance, and analyst boundary while defining its own analysis and recommendation criteria.
- The first cut does not require LLM calls to enable native capture or construct the deterministic index. The on-demand analyst call has model cost and may expose its bounded input to the selected model; the command should make that clear to the operator.

## Open decisions and implementation checks

- Complete the [navigation evidence spike](plans/spike-navigation-evidence.md) before finalizing the analyst input projection and report schema.
- Select a practical default analysis budget and define the CLI interaction for raising it or choosing among TARS-generated logical blocks when it is exceeded.
- Verify Codex Rollout Trace availability and reduction support in the supported CLI version, and verify how AoE can set a role-session-specific environment before launch.
- Implement and regression-test deterministic attribution of OpenCode native sessions to active AoE roles, including lanes where both roles use the same harness, using the role-specific launch handshake. Treat zero or multiple exact matches as a coverage error.
- Verify that a separate analyst session can read the worktree without mutating it for each supported author harness.
